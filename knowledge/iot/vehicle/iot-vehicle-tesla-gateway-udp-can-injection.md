## 一句话结论

科恩实验室破解特斯拉时发现，车网关把发往 UDP 20100/20101 端口的广播数据直接当作 CAN 报文转发到真实总线上；因此攻击者只要已控制车内任一可路由到网关的节点（如车机），无需 CAN 适配器和物理接线，向这两个 UDP 端口发送构造的 12 字节载荷即可伪造 CAN 帧，执行开后备箱、锁定/解锁车门等整车功能。

## 原理

- **网关是跨网段枢纽**：车内网络按域划分，车机（CID）等信息域节点与整车 CAN 总线之间通常由中央网关隔离/路由。网关固件除了转发诊断与业务帧，还可能内置"UDP→CAN 桥接"服务，用于车机侧进程发送控制信号。
- **该案例中的桥接行为**：网关监听 UDP 20100 与 20101 端口，把收到的 UDP 载荷直接封装为 CAN 报文并转发到真实 CAN 总线（原文未说明两个端口各自对应的总线/通道）。
- **为什么成立**：这个桥接只按目的端口和接收地址判断"这是车内合法信号"，不校验发送方身份、不要求认证或签名；CAN 帧本身又没有源身份与消息认证。于是任何能在车内网络发 UDP 包的节点（被攻破的车机、CID 上的任意进程）都等效于直接接在 CAN 总线上，可用普通 socket 伪造任意控制帧。
- **为什么危害大**：绕过物理接入（OBD/破线）与 CAN 适配器门槛，把"车机沦陷"直接升级为"整车功能控制"——原文示例即通过一条 UDP 报文打开后备箱，并可锁定/解锁车门；这也解释了车辆架构中网关隔离必须配合来源认证才有意义。

## 触发条件

- 已取得车内网络访问：车机/CID 被控制、ADB shell、或在车内网络中拥有可发包的据点，且能路由到网关地址。
- 目标网关固件存在 UDP→CAN 转发行为（该案例引自科恩实验室 Black Hat USA 2017 特斯拉研究“Free-Fall: Hacking Tesla from Wireless to CAN Bus”，见原文参考链接；原文未给出具体车型/固件版本）。
- 对应 CAN 通道上的执行器接受无认证的控制帧（该案例中的桥接帧直接上总线，未提及额外认证）。

## 利用步骤

1. 在车机侧确认网关地址（路由表、车机配置文件或 `ip route` 中的网关），确认与网关 IP 可达。
2. 向网关 UDP 20100 发送构造的 12 字节载荷；原文另提到 20101 端口（同样被当作 CAN 报文转发），可按响应情况在两个端口上试探。
3. 观察车辆响应（后备箱、门锁等）；按功能复用/微调载荷，逐个建立"载荷→功能"映射。
4. 若能在车机侧抓包或读取网关日志，可进一步确认 UDP 载荷与 CAN 帧的对应关系。

## PoC

原文给出的最小载荷示例（gw 为网关地址）：

```bash
# 打开后备箱
printf "\x00\x00\x02\x48\x04\x00\x30\x07\x00\xFF\xFF\x00" | socat - udp:gw:20100
```

说明：原文未公开该 12 字节到 CAN ID/数据段的字段映射，也未给出抓包对照，因此仅能复现"向 20100 发送该载荷触发开后备箱"这一动作；对其它功能需按同样方式试探构造。

## 变体与关联

- 变体：用 Python `socket.sendto()` 循环发送同一载荷，便于批量试探不同 ID/数据组合；原文提到网关同样处理 20101 端口，可在两个端口上分别尝试。
- 变体：广播地址（如 255.255.255.255）发送，适配网关监听广播的行为。
- 变体：作为"车机→整车"的横向移动跳板——先通过车机 ADB/OTA/浏览器等入口控制信息域，再以 UDP 桥接操作总线。
- 关联：[[iot-vehicle-obd-can-bus-access]]（物理接入读取 CAN 的前置入口）、[[iot-protocol-can-arbitration-id-discovery-spoofing]]（在总线上直接伪造 ID 的等价手法）、[[iot-vehicle-can-extended-frame-uds-ecu-discovery]]（网关后方的 UDS 探测）。

## 检测与防御

- 网关固件移除或严格限制 UDP→CAN 桥接：仅允许白名单进程/端口，桥接帧做来源校验与 CAN ID 白名单，拒绝任意载荷直通总线。
- 车内网络分段与防火墙：车机等信息域节点不得直接访问网关的控制类 UDP 端口，跨域流量走带认证的服务。
- CAN IDS 监控异常控制帧（门锁/后备箱等）出现的频率、来源与时序；对网关桥接日志做审计。
- 响应：隔离被控车机、审计网关配置与固件版本、升级网关固件并轮换车内服务凭据。
