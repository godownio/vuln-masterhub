## 一句话结论

找回密码页在「身份验证」步骤提供“验证方式不可用？”入口，点进去可以不经任何身份验证就把密保问题（安全问题）重设为自己知道的新答案，提交后流程状态直接变成「已验证」并跳到“重置密码”步骤，于是在只知道受害者账号的情况下即可改掉其密码并登录。

## 原理

- 账号找回流程的核心不变量是：**改变/重建认证因子之前，必须先证明对账号的控制权**。多因素找回（短信、邮箱、密保问题）中若某一种方式不可用，正确的降级做法是用另一种已绑定因子完成验证，或走人工审核。
- 本案的「重置认证方式」把“设置新密保问题”本身当成了身份验证：进入该页不要求已通过短信/邮箱验证，也不要求提供旧密保答案或旧密码；用户选择“安全问题”并填入新的问题/答案即可提交。
- 提交成功后服务端返回“设置成功”，前端（或服务端会话状态）把当前找回流程的“身份验证”步骤标记为已完成，直接跳转到第 3 步“重置密码”。也就是说，**攻击者刚刚写入的认证因子被立即当成了验证受害者的证据**，属于典型的自证循环（CWE-640 弱密码找回 / CWE-620 未验证的密码修改）。
- 该设计在前端表现为一个下拉框和链接，但根因在服务端：重置认证因子与账号找回流程共享同一流程状态，且缺少“先验证旧因子/其他因子”的步骤门禁。

## 触发条件

- 找回密码流程支持多种验证方式，并提供“验证方式不可用？”/“更换验证方式”一类入口；
- 进入“重置认证方式”页面不需要已通过任一因子验证（无短信/邮箱验证码、无旧密保答案、无旧密码）；
- 重置认证方式成功后，找回流程直接进入“设置新密码”步骤（步骤状态由服务端会话延续或前端可推进）；
- 系统允许把密保问题作为可重绑的认证方式。

## 利用步骤

1. 打开目标登录页，进入“忘记密码/找回密码”，输入受害者账号（如 admin 或任意已知用户名）进入身份验证步骤；
2. 点击右上角“验证方式不可用？”，进入“重置认证方式”弹窗；
3. 认证方式选择“安全问题”（也可尝试安全手机/安全邮箱，视其是否同样可无条件重绑）；
4. 任意填写新的安全问题与答案，提交，页面提示“设置成功”；
5. 流程自动跳到“重置密码”步骤（原文截图显示三步进度中“身份验证”已被打勾），设置新密码并提交，提示修改成功；
6. 用新密码登录受害者账号，进入个人中心，完成账号接管。

## 变体与关联

- 同一入口的其他形态：“更换密保”、“密保问题忘了？”、“手机号不用了？”、帮助中心里的“账号申诉/找回”链接，凡是能不经原因子验证就写入新因子的都应测试；
- 若重置认证方式后不能直接跳到改密，可检查流程是否把“已验证”状态放在可篡改的响应字段/前端状态里（对照库内客户端 step 参数跳过类卡片）；
- 与“密保问题弱设计可猜解”不同：本场景不需要猜答案，而是利用重绑入口把答案改成攻击者已知值。

## 检测与防御

- 服务端强制步骤门禁：重置任一认证因子前必须通过另一独立因子验证（原绑定手机验证码、原邮箱验证码、旧密码、人工审核至少其一），验证结果与账号绑定存入服务端会话；
- 重置认证方式成功后不得自动把账号找回流程标记为已验证，也不能直接进入改密步骤；改密必须重新走一次与账号绑定的验证；
- 对“重置密保/换绑”操作做风险控制：二次确认、延迟生效、向原绑定手机/邮箱发送安全通知；
- 监控同一会话在短时间内出现“重绑密保问题 → 设置新密码”的连续操作；监控大量账号触发该路径。
