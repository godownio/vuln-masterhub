## 一句话结论

登录页提示「评审专家可通过【专家入口】直接进入系统」但页面上并没有专家后台入口；任意填入账号口令抓包，把请求体里的用户名替换成 `expert`、验证码保持与原请求一致，重放即直接以专家角色进入后台——服务端把「用户名」当作可自由提交的角色选择器，而不是用口令校验身份，验证码又只校验会话不校验用户名，于是角色可任意指定。

## 原理

- 这类系统常把「角色」编码进账号名（`expert`/`admin`/`teacher`），登录接口的逻辑是「按用户名查用户 → 校验口令 → 按用户名解析角色」。若某个内置账号（`expert`）走了特殊分支（免口令、口令为默认值、或只校验验证码），替换用户名就等价于指定角色。
- 验证码的作用域是关键：如果验证码只与会话（cookie/session）绑定，而与本次提交的用户名无关，那么「先用任意账号触发验证码 → 再改用户名重放」就能复用同一个验证码，绕过「换账号需重新验证」的设计意图。
- 之所以成立，是因为服务端在「取用户名」和「取验证码」之间没有一致性约束：两者来自同一请求体，但分别独立校验，攻击者可以只改其中一个。
- 危害直接：进入后台即获得专家/管理员功能面（数据查询、导出、审核），无需知道任何真实口令；若后台还有文件下载/导出接口，可进一步扩大。
- 判别信号：登录页出现「XX 入口」「专家/评审/内部人员可直接进入」一类文案，往往意味着存在按角色名分流的内置账号或调试入口。

## 触发条件

- 登录接口接受客户端提交的 username 与验证码，二者未做一致性绑定。
- 系统存在按用户名分流的特殊账号（如 `expert`）或角色选择逻辑在客户端可见（隐藏入口、前端常量、页面文案）。
- 验证码在会话内可复用（不改用户名即可反复提交）。
- 目标未对登录请求做签名/防篡改（如整体 HMAC）。

## 利用步骤

1. 打开登录页，注意「专家入口」「内部入口」等提示文案，记录可能的角色名（`expert`、`admin`、`reviewer`、`teacher`）。
2. 输入任意账号口令，正常提交一次登录，抓取完整请求（含验证码字段与 cookie）。
3. 在同一会话下重新获取一次验证码（若页面要求），但**不更换会话**；把请求体中的用户名改为 `expert`，口令可保留原值或置空，验证码沿用上一步的值。
4. 重放请求，观察是否返回登录成功并下发会话；随后访问后台首页/任意功能页确认权限。
5. 若首次失败，尝试同义角色名、大小写变体（`Expert`、`EXPERT`）、以及带前后空格的写法，判断后端是否做了 `trim`/小写归一。
6. 进入后台后记录可见功能面与数据范围，作为越权证据；不要执行破坏性操作。

## PoC

```http
POST /login/index HTTP/1.1
Host: target
Content-Type: application/x-www-form-urlencoded
Cookie: PHPSESSID=<与验证码同一会话>

username=expert&password=<任意值>&captcha=<同一会话已获取的验证码>
```

响应为登录成功/跳转后台即确认；原始请求中用户名位置为 `expert`（捕获时被替换的字段）。

## 变体与关联

- 变体：把用户名换成管理员账号（`admin`）而口令留空/默认，若后端对内置账号免校验，同样可进；需要先从前端 JS 或提示文案拿到账号名。
- 变体：角色改由独立参数控制（`role=1`、`userType=expert`）时，直接改该参数；验证码仍可复用。
- 变体：验证码与用户名绑定但校验顺序错误（先校验验证码、后换用户名）时，可在校验后、入库前篡改字段（需能控制中间层）。
- 关联：[[web-generic-auth-edu-expert-channel-path-concat-admin-takeover]]（同样围绕「专家通道」的多入口权限不一致，但走的是路径拼接越权而非登录参数替换）。
- 关联：[[web-generic-auth-2fa-user-parameter-tampering-code-bruteforce]]（登录/二次验证环节 username 参数篡改的同类思路）。

## 检测与防御

- 防御：登录接口不要用用户名作为角色选择器；角色必须由服务端根据「已认证身份」查表得出，且内置/调试账号在生产环境删除或强口令+多因素。
- 防御：验证码与会话绑定并在校验成功后立即失效；同一请求内校验「验证码对应的会话」与「提交的用户名」一致性，或干脆在验证码校验通过后不允许再改用户名。
- 防御：登录请求整体加签（防篡改），后端对 username 做白名单字符与长度校验。
- 检测：日志中检索同一会话内 username 字段变化后仍登录成功的记录；对 `expert`/`admin` 等特殊账号的登录来源做重点审计。
- 检测：把「登录页出现专家/内部入口文案」的前端常量纳入资产梳理，逐一验证对应账号是否仍存在。
