## 一句话结论

登录接口若只按手机号/用户名查出用户对象就建立会话，而没有把提交的口令与库中 password hash 做校验，则任何已知手机号配任意随机字符串都能登录；文章在拿到全站用户手机号后，用一个弱口令输入登录框即进入教师/管理员后台，并声称站内所有用户手机号都可这样登录，密码形同虚设。

## 原理

- 正常认证必须完成两步：按账号取出用户记录，再用 bcrypt/argon2/PBKDF2 等对提交口令做哈希比对；只有比对成功才签发会话。若代码只做了第一步（`SELECT * FROM user WHERE phone=?` 后判断 `user != null`），口令字段根本不参与判断，第二步缺失。
- 常见成因：登录分支只判断用户存在、密码校验被注释/短路（`if (user != null || checkPassword(...))`）、开发环境 mock 认证被带到生产、只在前端校验密码格式、单点登录/短信登录分支复用同一会话签发逻辑但未校验凭据。
- 文章场景：登录框以手机号为账号，攻击者先通过未授权 `user/all` 接口拿到全站手机号；对其中一个账号输入弱口令/任意字符串即登录成功，页面显示教师姓名并具备管理员功能（增删改查用户、审核等）。
- 该缺陷与“弱口令”不同：弱口令是猜中了真实口令，而这里口令值不参与比对，任意字符串（包括多个不同的随机串）都应成功；验证时应使用多个互不相同的随机口令并换多个账号复现，以排除“恰好是弱口令”的巧合。
- 一旦登录的是管理员/教师角色，后续可结合 IDOR（改 `user_id`）编辑他人资料、同意/拒绝审核，扩大影响。

## 触发条件

- 目标登录接口以手机号/用户名为主键，且服务端存在“只查用户、不比对密码”的缺陷。
- 攻击者已知至少一个有效账号（可通过未授权用户列表、注册功能、公开通讯录、手机号枚举等方式获得）。
- 登录入口没有被 MFA、短信验证码、设备绑定等二次校验阻断；图形验证码可通过识别或复用会话处理。
- 该账号未被禁用/锁定，角色具备可操作的功能点。

## 利用步骤

1. 先获取有效账号：注册一个普通账号进入系统，或通过未授权接口（如 `user/all`）拿到手机号列表；手机号通常就是登录名。
2. 在登录框输入目标手机号与一个随机字符串（不要用常见弱口令），提交并观察是否返回 token/会话或跳转后台。
3. 换用不同随机字符串、再换 2-3 个不同账号重复，确认不是弱口令巧合；同时用不存在的手机号做对照，确认失败路径。
4. 若登录成功，检查当前用户角色与菜单：文章登录后显示教师姓名，并可直接进行用户增删改查、审核等管理操作。
5. 在后台逐个测试功能点，结合 `user_id` 等参数做越权（编辑资料、同意/拒绝审核），扩大影响。
6. 记录请求/响应作为证据；测试时控制频率，避免触发账号锁定或业务告警。

## 变体与关联

- 变体：只对某些角色/内部账号跳过密码校验；外部注册账号正常校验，内部员工账号可任意登录。
- 变体：短信验证码登录分支不校验验证码或使用固定万能码；与密码登录共用会话签发。
- 变体：登录成功但权限受“待审核”限制（文章注册账号即如此），此时先用任意密码登录管理员/已审核账号才能拿到实际权限。
- 边界：服务端正确调用 `password_verify`/`bcrypt.checkpw`、启用 MFA、账号锁定、验证码强校验时，本手法不成立。
- 关联：[[web-generic-auth-wordpress-rest-header-password-check-missing]]（同样“只查用户不验密码”的代码级案例，CVE-2026-9179）、[[web-generic-auth-proxy-history-unauth-user-all-leak]]（本文前置的用户列表泄露）、[[web-generic-auth-authenticated-change-password-idor]]（登录后的越权改密）、[[web-generic-auth-multi-session-matrix-leakscore]]（登录后权限矩阵测试）。

## 检测与防御

- 检测（测试方）：用多个不同随机口令、多个账号做交叉验证，排除弱口令巧合；对比不存在账号的响应差异；检查登录响应是否直接返回 token/角色信息。
- 检测（防御方）：审计所有登录分支是否调用密码哈希校验函数；对登录失败/成功日志做异常分析（同一账号短时间多个不同口令仍成功是强信号）；监控同一 IP 对大量手机号的登录尝试。
- 修复：登录必须校验 password hash（bcrypt/argon2，恒定时间比较）；禁止任何“只查用户就建会话”的短路分支；统一认证入口，删除 mock/测试分支。
- 加固：启用 MFA/短信二次验证、账号锁定与速率限制；验证码服务端强校验；对管理员账号增加设备/来源限制；定期做认证逻辑的安全测试与代码审计。
