## 一句话结论

点开某个功能模块时页面提示「无权限」，抓包发现后端只是返回一个业务码（本例 `1` = 无权限），前端据它决定是否跳转/渲染；用 Burp 拦截响应把该码改成 `0` 再放行，受限模块的页面就被渲染出来——能否真正看到数据取决于该模块背后的接口是否另做服务端鉴权，因此这一步必须随后用「页面里的列表请求能否成功」来定级。

## 原理

- **模块入口的权限判断被放在前端**：很多中后台在「进入模块」时先请求一个 `checkPermission` 类接口，返回 `{code:1, msg:'无权限'}` 或 `{code:0}`；前端拿到后决定 `location.href` 跳不跳、菜单渲不渲染。业务码是「展示层的开关」，不是服务端签发的授权凭证。
- **响应在客户端可改**：Burp/代理拦截响应，把 `code` 值（或 `success:false`、`statusCode:403`、`hasPermission:0`）改为成功值，前端逻辑即走「允许进入」分支，路由跳转与组件渲染都会执行。
- **真实危害取决于后端接口**：如果模块内每个数据接口都独立校验了角色，改包只能看到一个空壳/报错页；如果数据接口只校验「已登录」，那么页面能正常拉到数据，等同于完整的垂直越权。原文改包后成功进入页面，说明该模块接口未做功能级授权。
- **与登录响应篡改的区别**：登录处的 `resultCode` 篡改是为了「没有会话也能进后台」；本条是「已有低权限会话，把没有权限的模块强行打开」，两者都属于「客户端信任业务码」，但发生在授权链路的不同阶段。
- **为什么值得单列**：这类页面级绕过在真实系统里极常见，且是「功能级授权缺失」的快速验证手法——它把「找越权接口」的成本降到「点一遍菜单 + 改一个数字」。

## 触发条件

- 中后台系统，模块/菜单的显示与跳转由前端依据接口返回的业务码决定。
- 该接口返回的业务码是明文数字/布尔（`code`、`status`、`hasAuth`、`permission`），未与签名或服务端会话绑定。
- 攻击者能拦截并修改响应（Burp/代理/浏览器插件）。
- 模块内的数据接口未做功能级（角色/权限点）校验时，危害升级为完整越权。

## 利用步骤

1. 用低权限账号登录，点击提示「无权限」的模块，抓取该次请求与响应。
2. 在响应里找判定字段：`code`、`status`、`success`、`hasPermission`、`permission`、`msg`（文案常与字段值对应，如 `1` 配「无权限」）。
3. Burp 开启响应拦截，把该字段改为成功值（`1 → 0`、`false → true`、`403 → 200`），Forward 放行。
4. 观察浏览器：页面是否被渲染、菜单是否出现、是否发生路由跳转。
5. **定级验证**：在页面里触发一次数据加载（列表/详情/导出），抓该接口请求。若返回真实数据 → 服务端缺功能级授权，属完整垂直越权；若 401/403 或空数据 → 仅为前端绕过，危害降级。
6. 只做必要验证（如读一页列表），不要批量导出或修改数据。

## PoC

```text
POST /api/module/checkPermission HTTP/1.1
Content-Type: application/json

{"moduleId":"finance"}

HTTP/1.1 200 OK
{"code":1,"msg":"无权限","data":null}
```

拦截响应改为：

```json
{"code":0,"msg":"","data":{"moduleId":"finance","url":"/finance/index"}}
```

前端放行后页面渲染，再验证模块内接口：

```text
GET /api/finance/list?page=1 HTTP/1.1
Cookie: <低权限会话>

HTTP/1.1 200 OK
{"code":0,"data":{"total":1284,"rows":[...]}}      // 服务端未校验角色 → 真实越权
```

改包常见字段对应关系：`code:1→0`、`success:false→true`、`status:403→200`、`hasPermission:0→1`、`permission:false→true`。

## 变体与关联

- 判定载体变体：业务码字段、HTTP 状态码、响应体里的 HTML 片段（把「无权限」区块删掉/改为目标菜单）、JS 变量（`window.hasAuth=false`）。
- 前端控制变体：路由守卫（Vue/React Router）、按钮级 `v-if`/`v-show`、菜单接口返回的树；改响应或改本地状态都能绕过页面限制，但都不改变服务端行为。
- 危害升级路径：页面绕过 → 模块内接口无鉴权（真实越权）→ 接口支持写操作（越权改数据）→ 接口支持导出/批量（数据泄露规模化）。
- 关联：与「登录响应 resultCode 改 0 进入后台」同属客户端信任，但那条针对登录、本条针对模块授权；与「响应 JS 定时器篡改绕过登出」的区别是那条改的是生命周期检查，本条改的是授权判定；与「功能级授权缺失（拦截器只验登录不验角色）」的关系是本条常被用来**快速发现**那张卡描述的问题——页面打开后再看接口是否放行。

## 检测与防御

- 模块入口的权限必须由服务端裁决：接口返回的应是服务端会话中的真实权限集合，且模块内每个数据接口都独立做功能级校验（权限点/角色注解），不依赖前端开关。
- 不要把「是否允许进入」做成客户端可决定的一次性业务码；若必须给前端菜单，也应只用于渲染，不承担授权职责。
- 对越权访问记录审计日志（用户 + 模块 + 接口 + 结果），并对「同一会话短时间访问多个未授权模块」告警。
- 前端加固仅作纵深：路由守卫、隐藏菜单都可绕过，不能作为安全边界。
- 检测：响应中 `code`/`hasPermission` 等字段被代理改写无法从服务端感知，因此检测重点应放在**服务端接口层的异常授权**：低权限角色访问高权限接口、同一 token 跨模块高频请求。
