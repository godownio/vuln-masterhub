## 一句话结论

找回密码流程在输入邮箱后自动发送验证码，而"给谁发码"只取决于请求里的邮箱参数、"这笔重置属于谁"却保存在会话状态里，两者没有强绑定：把发码请求同会话并发成两份（一份受害邮箱、一份攻击者自己的邮箱），两份都能成功、两个邮箱各收到一个验证码；之后由于改密校验只比对会话中的验证码而不复核邮箱归属，攻击者可以用自己邮箱收到的验证码完成受害账号的密码重置。

## 原理

- **重置流程的状态存放**：典型实现是：第一步提交邮箱 → 服务端把"待重置账号/邮箱"和"本次验证码"写入会话 → 第二步提交验证码 + 新密码 → 服务端比对会话里的验证码后改密。正常流程中"发码对象"与"会话待重置账号"是同一次请求写入的，看似一致。
- **竞态点**：发码请求本身携带邮箱参数，服务端用它决定收件人，但验证码写入的是会话里同一个槽位。并发发送两份请求时：两份都能通过"发送间隔/未过期"检查（见 `[[web-generic-race-condition-sms-rate-limit-concurrency-bypass]]` 同型先查后写），且两个验证码先后写入会话——如果受害账号的流程状态仍然保留在会话里，而会话中的验证码槽位被攻击者邮箱那份覆盖（或校验逻辑只比对验证码值、不校验验证码所属邮箱），攻击者手里就有一个能通过校验的码，且改密落点仍是受害账号。
- **为什么必须并发**：串行时第二次发码通常会刷新/作废前一个验证码，攻击者只能拿到其中一个码；并发让两次发码都认为自己是"第一个请求"，从而两个邮箱都能收到有效（或至少可被用于校验）的验证码。
- **配合点**：发码后不能再触发任何重发请求——重发会刷新验证码导致手里那个码失效；因此提交改密前要确保没有其他页面/拦截器自动重发。
- **证据强度说明**：原文只展示了两个邮箱同时收到重置邮件、并发发码接口均返回成功，最终"输入验证码改密成功"为作者口述，未给出成功截图；服务端具体绑定逻辑为推断。实际验证时应分别确认：改密接口是否只校验验证码值、验证码是否与会话而非邮箱绑定、并发发码是否让两个码同时有效。

## 触发条件

- 找回密码第一步由请求参数（如 `email`）决定发码对象，同时把待重置账号/验证码存入会话。
- 发码接口的"检查是否刚发过 → 写入验证码 → 发送"不是原子操作，同一会话可并发触发多次。
- 改密/校验验证码的接口只比对会话中的验证码值（或按会话取验证码），不校验该验证码发送到的邮箱与当前待重置账号是否一致。
- 攻击者知道受害者的邮箱/账号，且站点允许用该邮箱发起找回流程；验证码邮件无"此码仅用于 XX 账号"的强绑定展示或绑定校验。

## 利用步骤

1. 用自己的账号完整走一遍找回密码流程，抓取每一步请求，确认输入邮箱后自动触发的连续请求（本例为两个连续数据包），区分"发送验证码"请求与页面加载/校验请求。
2. 正常流程下确认验证码与邮箱/账号的绑定关系：用 A 邮箱收码、改 B 账号的密码是否会被拒；记录改密请求的参数与会话状态。
3. 对受害者邮箱发起找回，抓取发码请求；复制一份，把邮箱参数改成攻击者自己可控的邮箱。
4. 将两份请求放入同一并行组（Burp Repeater `Send group (parallel)` 或 Turbo Intruder 同 gate），同时发送；确认两份响应均为成功。
5. 分别登录两个邮箱，确认各收到一个验证码邮件（受害邮箱与攻击者邮箱）。
6. 回到仍在受害者重置流程中的浏览器会话，确保没有触发重发（关闭拦截/避免刷新页面导致自动重发），输入攻击者邮箱收到的验证码 + 新密码提交。
7. 若改密成功，用新密码登录受害者账号验证；失败则检查是否验证码与会话/账号绑定、重发是否已作废旧码，评估是否需要调整并发时序。
8. 成功后立即停止，记录时间线与请求证据，不扩大影响。

Host: target
Content-Type: application/x-www-form-urlencoded
Cookie: SESSION=<仍在受害者重置流程中的会话>

## 变体与关联

- **绑定缺陷变体**：有的站点在发码时把验证码按邮箱存库（key=email），改密时却按会话里的账号取验证码——并发改邮箱后邮箱与账号错位；有的用同一个验证码字段多步复用，改密接口不复核邮箱。
- **不做竞争也可测**：先串行尝试"给受害邮箱发码后再把请求邮箱改成攻击者邮箱重发，再用攻击者邮箱的码改密"，若被拒才是竞态窗口的用武之地；也可测试"发码后修改会话中的目标账号"类缺陷。
- **关联**：密码找回的步骤跳过/身份篡改路线见 `[[web-generic-auth-password-reset-step-param-final-skip-username-cookie]]`；发码频控并发绕过见 `[[web-generic-race-condition-sms-rate-limit-concurrency-bypass]]`；验证码并发复用见 `[[web-generic-race-condition-captcha-one-time-multi-use-login-bruteforce]]`。
- **边界**：若验证码与 (会话, 邮箱, 账号) 三元组强绑定、或改密接口重新校验邮箱归属，本场景不成立。

## 检测与防御

- **强绑定验证码**：验证码记录必须包含 `session + 目标账号/邮箱 + 用途 + 过期时间`，校验时四者全部比对；改密接口使用的账号只能来自服务端状态，不能来自请求参数或可写 Cookie。
- **原子发码**：同一会话/同一账号的发码请求加互斥锁与幂等键，单位时间内只允许一次成功；新码下发时显式作废旧码并记录。
- **一次性消费**：验证码校验成功后原子删除（`GETDEL`/条件更新），失败计数也计入限频。
- **检测信号**：同一会话在极短时间内对多个不同邮箱发起找回；改密请求中的验证码与最近一次发码的邮箱不一致；同一账号密码重置前后出现多个并发发码请求；重置邮件被发往非账号绑定邮箱。
