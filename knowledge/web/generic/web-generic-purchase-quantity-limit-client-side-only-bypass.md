## 一句话结论

商品页的「每人限购 N 件」「单次最多买 N 件」如果只是在页面上用 JS 限制输入框的最大值（`max` 属性、按钮禁用、`if (num > limit)` 拦截），而下单接口不校验数量上限，那么抓包把 `num`/`quantity`/`buyCount` 改成远超上限的值提交，服务端就会按该数量生成订单——限购形同虚设，可用于抢购囤货、绕过促销名额、批量套取优惠资格。

## 原理

- **校验位置放错**：前端限制只影响 UI 交互，请求可以被代理工具任意构造。数量上限属于业务规则（限购、库存、促销资格），必须由服务端在「加购/下单/支付」每一步校验。
- **为什么服务端常常漏掉**：页面已经做过 `max` 与 JS 拦截，开发容易认为「用户改不了」；下单接口往往只校验「数量为正整数」「不超过库存」，而库存通常远大于限购数，于是数量上限这一维度缺失。
- **与「改总价」的区别**：本卡不改金额也不改商品，只放大数量。即使服务端按「单价 × 数量」正确计算总额，攻击者仍以合法金额买到了超限数量——损害在业务规则（限购、名额、库存公平性）而非支付金额。
- **常见被连带绕过的约束**：限购名额（每人 2 件）、促销资格（前 100 名）、秒杀单人上限、优惠券「每单限用 N 件」、赠品「满 N 件送」。放大数量后可能一次性吃完库存或批量占用赠品。
- **判断依据**：把数量改成明显超过上限的值后，若响应仍返回「下单成功」且订单详情数量等于提交值，即证明服务端未校验上限；若被拦，注意区分「库存不足」与「超过限购」两种报错，前者说明只校验了库存。

## 触发条件

- 商品/下单流程有数量上限（限购、单次上限、活动名额），页面存在可见的前端限制。
- 下单或加购接口接收客户端提交的数量，服务端未对该值做上限校验（或只校验库存与正数）。
- 攻击者账号满足购买资格（已登录、有购买资格、活动在有效期内）。
- 库存或名额足够容纳放大后的数量（否则会被库存校验挡住，需缩放到刚好可用的值）。

## 利用步骤

1. 定位限制位置：在商品页尝试输入超过上限的数量，观察是否被输入框 `max`、按钮禁用或 JS 弹窗拦住；据此确认「限制只在前端」。
2. 抓取「加入购物车」或「立即购买/提交订单」请求，记录数量字段名（`num`、`quantity`、`buyCount`、`goodsCount`、`skuNum` 等）与当前值。
3. 把数量改成超过上限的值（如限购 2 改成 100），其余字段不动，重放请求。
4. 观察响应：若返回成功，查看订单详情/购物车里的实际数量是否为 100；若报错，记录错误文案，判断是「库存不足」还是「超限」，后者说明服务端有校验，本条不成立。
5. 若被库存挡住，把数量调到「刚好等于剩余库存」或分多笔订单累计突破限购（每笔都在上限内，但总量超限），检验服务端是否按用户 + 商品累计校验。
6. 记录证据（请求、响应、订单详情）后停止；评估影响：是否吃满库存、是否占用了限量名额/赠品。

```json

```

判据：`num=100` 时响应仍为成功，且购物车/订单详情显示数量 100（而非被服务端裁剪回 2）。

累计突破（单笔不超限、总量超限）的判断：

```text
第 1 单 num=2 → 成功
第 2 单 num=2 → 成功
...
第 n 单 num=2 → 仍成功且无「已达上限」提示 ⇒ 缺按用户+商品累计校验
```

## 变体与关联

- 字段变体：`num`/`quantity`/`buyCount`/`goodsCount`/`skuNum`/`amount`；有时数量藏在数组元素里（多商品同时提交），只改其中一个。
- 类型变体：把数量写成字符串、浮点、超大整数、负数（负数与金额抵消的组合见负数量卡）；校验只做 `parseInt` 或正则时可能被绕过。
- 累计变体：单笔限制生效但缺少「按用户 + 商品累计」统计，分多笔突破；或并发多笔同时通过「未超限」检查（并发类问题）。
- 关联：[[web-generic-payment-negative-quantity-offset]]（负数量抵消金额）、[[web-generic-points-mall-goodsid-points-parameter-tampering]]（改商品编号/积分替代改数量）、[[web-generic-race-condition-coupon-order-submit-reuse]]（并发下同一资格被多次使用）。

## 检测与防御

- **服务端校验**：加购、下单、支付三处都校验数量为「大于 0 的整数且不超过限购上限」；上限按活动/商品配置在服务端读取，不信任客户端。
- **累计统计**：按「用户 + 商品 + 活动」累计已购数量，下单时在事务内校验并自增，防止分多笔突破与并发绕过。
- **库存与名额**：库存扣减与限购校验放在同一事务或原子操作中；名额类活动用唯一约束防重复占用。
- **检测信号**：单笔数量远超页面配置上限；同一用户对同一商品短时间多笔订单且总量超过限购；数量字段出现非整数/超大值；请求数量与页面 `max` 不一致。
