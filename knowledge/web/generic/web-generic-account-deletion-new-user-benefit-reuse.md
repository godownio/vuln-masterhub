## 一句话结论

当应用把“新用户”判定为“当前用户表里没有这个邮箱/手机号”，并且在账号注销时物理删除用户及其权益记录时，攻击者可以“注册领新人权益 → 使用一部分 → 注销 → 用同一邮箱/手机号重新注册 → 再次被判定为新用户”，无限循环领取本应只发一次的新人福利，造成运营资损。

## 原理

- 注册逻辑通常只查当前有效用户：
  ```java
  if (userRepository.findByEmail(email) != null) throw new RuntimeException("邮箱已注册");
  ```
  注销逻辑直接 `userRepository.deleteById(userId)` 物理删除整条用户数据；用户表与权益表配置了级联删除，账号删除后领券记录同步消失。
- 权益发放逻辑只检查“当前账号是否已有权益”：
  ```java
  if (user.getCoupons().isEmpty()) { /* 发放 NEW_USER_100 */ }
  ```
  它不查询该邮箱/手机号/设备/IP 的历史领取记录；账号被物理删除后，历史记录也不存在，系统自然认为这是全新用户。
- 注销模块与营销风控模块割裂：注销不会更新风控台账，营销发券也不会读取注销历史；注册接口没有 IP/设备/手机号频次限制与冷却，脚本可以批量循环。
- 四个缺陷叠加：单一身份字段（邮箱/手机号）+ 物理删除无台账 + 权益发放只看当前账号 + 无注册风控。缺一不可：如果保留历史台账，注销后仍能识别；如果注册有频次限制，批量循环会被拦；如果发券查历史，当前账号为空也不够。
- 根因是“账号数据生命周期与营销风控体系脱节”，不是某个接口的参数校验错误；扫描器很难发现，因为攻击流量与正常注册/注销/领券操作高度相似。

## 触发条件

- 应用提供新用户福利（免费时长、优惠券、试用会员、注册红包等），且按账号维度只发一次。
- 注销流程物理删除用户数据，或级联删除权益/订单/领取记录，没有独立的历史台账或软删除标记。
- 注册/新用户判定只查当前用户表，未叠加设备指纹、IP、实名信息、手机号/邮箱历史。
- 权益发放只检查当前账号状态，不查询全生命周期领取记录。
- 注册/注销接口没有频次限制、冷却、验证码或风控策略，允许脚本批量循环。

## 利用步骤

1. 准备一个全新临时账号（邮箱/手机号），登录后确认系统自动下发新人权益（如 2 天免费时长）。
2. 正常使用一部分权益（如等待剩余时长降到 1 天），让行为看起来像真实用户，降低异常特征。
3. 执行账号注销，并清空本地缓存/重新安装，确保客户端不保留旧身份。
4. 让系统重新下发临时账号，或直接用同一邮箱/手机号重新注册；服务端因原记录已被物理删除，判定为全新用户。
5. 再次领取完整新人权益；重复“使用一部分 → 注销 → 重注册 → 领取”，形成循环。
6. 用脚本/多账号批量执行，评估可复用的权益总量与资损；注意频率与设备/IP 特征，避免触发风控。

## PoC

文章为抽象业务场景，未给出具体目标的 HTTP 请求；按业务接口顺序的最小复现思路：

```text
1. POST /register  {email: attacker@example.com, password: ...}
2. POST /login     获取会话，系统自动发放新人权益（2 天）
3. 使用权益至剩余 1 天
4. POST /account/delete  注销账号（服务端物理删除用户及权益记录）
5. 清空客户端缓存/重装
6. POST /register 同一 email（或同一手机号）→ 系统判定全新用户
7. 再次获得 2 天新人权益，回到步骤 3 循环
```

判定点：

```text
注册响应/登录响应中出现“新人权益”“免费时长”“NEW_USER”等字段；
注销后再次注册，权益从 0 恢复为完整额度；
同一邮箱/手机号在短时间内多次注册成功。
```

## 变体与关联

- **权益变体**：新人优惠券、免费试用会员、注册红包、首单立减、免费额度、邀请奖励；凡是“按账号只发一次”的权益都可能被复用。
- **身份变体**：邮箱、手机号、设备指纹、IP、实名信息、第三方 OpenID；只查单一字段时最容易绕过。
- **删除变体**：物理删除、级联删除、缓存过期、账号合并/迁移导致历史丢失；软删除 + 独立台账可防御。
- **风控变体**：注册频次限制、设备/IP 冷却、行为验证码、同人多账号识别、营销黑名单。
- **关联**：[[web-generic-client-side-score-trust]]（客户端信任/业务逻辑滥用）；[[web-generic-payment-negative-quantity-offset]]（业务参数逻辑漏洞）；[[web-generic-payment-amount-tamper-no-order-binding]]（订单/金额逻辑缺陷）；[[web-generic-race-condition-tip-reputation-role-escalation]]（并发/权益类逻辑）。
- **边界**：若注销保留软删除与历史台账、发券查全生命周期、注册有频次/设备风控，本路径失效；仅用于授权安全测试与防御研究。

## 检测与防御

- **检测**：同一邮箱/手机号/设备在短时间内多次注册-注销-领券；注销后立即重新注册；新人权益领取记录与账号生命周期不匹配；注册接口高频调用。
- **防御**：账号注销改软删除（`is_deleted`、`deleted_at`），保留用户与权益历史；建立独立的权益领取台账，账号注销不删除台账。
- **身份识别**：叠加手机号、邮箱、设备指纹、IP、实名信息等多维度判定新用户，不只查当前用户表。
- **风控**：注册/注销接口加频次限制、冷却、验证码与设备/IP 风险评分；发券前查询全生命周期领取记录；对异常循环告警。
- **审计**：记录注册、注销、发券、核销的完整链路，支持按身份追溯；定期审计新人权益领取分布与资损。
