## 一句话结论

攻击者先把带 SQL 元字符的数据提交给一个会正确转义/参数化的“写入”接口，Payload 以原始字符形式落库；应用随后从数据库读出该值，误以为“数据库里的数据是安全的”，直接拼接进另一条 SQL，注入才在第二阶段触发。

## 原理

- 一次注入发生在“输入 → SQL”路径：如果写入使用参数化查询或正确转义，单引号等字符会被安全存储，第一阶段不会报错，也不会执行恶意 SQL。
- 二次注入发生在“数据库 → 输出 → 新 SQL”路径：应用把从数据库读出的值当作可信数据，直接拼进第二条语句，没有再次参数化。
- 典型的信任边界错误是“入库时过滤了，所以出库后不用过滤”。但数据库只是存储介质，存进去的字节（包括引号、注释符）不会被自动净化；写入时的转义只对那一次查询有效，不会改变存储内容。
- 因此只要存在“读取—拼接”的代码路径（改密码、导出报表、后台审核、订单查询、模板渲染后再查询），且读取值包含可控字符，就能闭合 SQL 结构。
- 二次注入往往比一次注入更隐蔽：第一阶段请求完全合法，WAF 和日志中看不到 SQL 关键字；Payload 可能在其他用户、后台管理员或定时任务触发时才生效。

## 触发条件

- 应用有“写入数据库”和“读取后拼接 SQL”两段逻辑，且两段使用不同的安全处理。
- 第一阶段允许攻击者控制某个字段（用户名、昵称、地址、备注、文件名、标签等），并能把引号、注释符等字符原样存入。
- 第二阶段从数据库读出该字段后，直接拼接进 SQL，没有参数化或重新转义。
- 攻击者能触发第二阶段（登录、改资料、后台审核、报表导出等）。

## 利用步骤

1. 找到会落库且后续会被读取使用的字段（注册资料、个人简介、订单备注、文件名、分组名）。
2. 在第一阶段提交带 SQL 元字符的值，确认写入成功且没有被改写（回显或再次读取该字段验证）。
3. 找到读取该字段并执行 SQL 的功能点。
4. 构造能闭合第二阶段 SQL 结构的 Payload，例如修改密码、查询其他用户、联合查询。
5. 观察第二阶段响应或数据库状态变化，确认注入生效。
6. 若第二阶段无回显，改用布尔/时间条件或带外通道。

## PoC

场景：注册/资料修改时用户名可自定义，写入使用参数化；后台“修改密码”功能从数据库读出用户名后拼接 SQL。

```sql
-- 第一阶段：把用户名设为（末尾带空格或注释符）
admin'-- 
```

数据库实际存储的字符串就是 `admin'-- `（引号并未被删除，只是写入时被安全转义）。

```sql
-- 第二阶段：应用读取该用户名后拼接
UPDATE users SET password='NewPass123' WHERE username='admin'-- '
```

拼接后条件变成 `username='admin'`，后面的原密码校验或条件被 `-- ` 注释掉，攻击者改掉 admin 的密码。

另一个数据回读型例子：

```sql
-- 第一阶段存入昵称：test' OR '1'='1
-- 第二阶段报表查询拼接：
SELECT * FROM orders WHERE owner='test' OR '1'='1'
```

## 变体与关联

- 变体：存储的 Payload 在后台审核、导出、定时任务中触发，攻击者本人不直接访问第二阶段接口。
- 变体：字段先经过 HTML 编码或 JSON 编码，读取后被解码再拼接，需要在存储时构造能通过外层编码的值。
- 变体：动态表名/列名/ORDER BY 无法参数化，二次注入常出现在这些标识符位置。
- 关联：[[web-generic-sqli-http-header-injection]]（请求头值落库后在别处拼接）。
- 关联：[[web-generic-sqli-java-identifier-table-order-by-injection]]（标识符位置的拼接注入）。

## 检测与防御

- 修复：所有 SQL 一律参数化，包括从数据库读出的值；不要因为数据来源是数据库就信任。
- 修复：动态表名/列名/排序字段使用白名单映射，不接受任意字符串。
- 加固：统一数据访问层，禁止业务代码手写字符串拼接；代码审计重点搜索“查询结果 → 字符串格式化 → 再查询”的路径。
- 检测：同一账号先写入含引号/注释符的资料，随后触发改密、导出等操作；数据库中异常的用户名/备注；SQL 日志里出现由历史数据拼接出的异常语句。
- 响应：排查所有读取用户可控字段并拼接 SQL 的功能点，而不只是入口参数。
