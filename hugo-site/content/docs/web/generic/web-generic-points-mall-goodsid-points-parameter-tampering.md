## 一句话结论

积分兑换/下单接口若把「兑换哪个商品（`goodsId`/`productId`）」「本次抵扣多少积分（`points`/`integral`/`score`）」当作客户端提交的普通参数，并且服务端只按这个编号去查商品、按这个数值去扣减，那么攻击者在提交订单时把编号改成更高价位的商品（如用 100 积分档的编号换成 1000 积分档的编号），就能以低积分换走高价值商品；反之把抵扣积分改成更小的值，则能少扣积分却照样发货。根因是「价格与商品由客户端指定、服务端只做算术不做绑定校验」。

## 原理

- 正常设计应是「客户端提交商品与数量 → 服务端按商品表查出单价/所需积分 → 服务端计算应付并校验用户余额 → 扣减并下单」。一旦把「应付金额/所需积分」也交给客户端，或在下单时才按客户端给的编号重新定价而不再校验该编号与用户选择的商品一致，定价权就落到攻击者手里。
- 典型的两种篡改点：
  - **商品编号**：请求体里 `goodsId=001`（100 积分档）改成 `goodsId=005`（1000 积分档）。服务端用新编号查商品、算出 1000 积分应付，但若前面已按 001 校验过余额/生成过订单快照，就会出现「校验用低价商品、发货用高价商品」的不一致。
  - **抵扣积分/金额**：请求里 `points=1000` 或 `integral=1000` 改成 `1`。服务端若信任该值作为「本次扣减额」，用户实际只被扣 1 积分。
- 与「只改总价」的区别：改总价（`totalAmount`）攻击的是支付金额字段；本卡攻击的是**商品标识与计价依据**，即使服务端对总价做了二次计算，只要编号可换且不校验归属/档位，仍然成立。
- 这类不一致通常来自「订单快照与结算逻辑分处两地」：前端页面按 A 商品展示、生成订单时按请求里的 B 商品落库，而校验发生在更早的一步（如进入结算页时）。服务端缺少「同一订单从选择到支付商品编号不可变」的约束。
- 危害随业务放大：积分可被刷成负值或绕过兑换门槛、实物商品被低价换走、虚拟权益（会员/卡券）被批量兑换。

## 触发条件

- 存在积分兑换/下单流程，请求中出现商品编号、所需积分/金额等可读参数。
- 服务端按客户端提交的编号查询商品与定价，且未校验该编号与「用户此前选择的商品/购物车条目/订单快照」是否一致。
- 服务端把客户端提交的抵扣积分或应付金额直接用于扣款/扣积分，或只做范围校验（如「必须为正」）而不核对与商品档位的对应关系。
- 账户有可用积分或余额（用于通过第一道校验）；越权/篡改发生在提交订单或支付环节。

## 利用步骤

1. 正常走一遍兑换流程，抓取「提交订单/确认兑换」的请求，记录所有与商品、积分、金额相关的字段（`goodsId`、`skuId`、`points`、`integral`、`amount`、`totalPoints` 等）。
2. 先做基线对照：不改任何字段提交一次，记录响应与订单详情里的商品名与扣减积分，确认服务端返回的扣减额与页面一致。
3. 篡改商品编号：把低价档商品的编号改为高价值商品的编号（先在商品列表接口里取到目标编号），其余字段不动，提交并查看订单详情里的商品名、所需积分与实际扣减。
4. 若第 3 步被拦（提示积分不足或商品不匹配），改篡改抵扣积分/金额：把 `points`/`amount` 改成更小的值（如 1 或 0.01），观察是否只扣该值却仍生成订单。
5. 组合两种篡改：低档编号 + 高价值发货，或高价值编号 + 极小抵扣值；以「订单创建成功且扣减额低于商品所需」为成功判据。
6. 复核订单状态与发货/权益发放是否正常，评估可重复次数（是否限购、是否校验库存），记录证据后立即停止，避免影响真实业务数据。

## PoC

无原始报文可公开引用，篡改形态如下（字段名按实际接口替换）：

```http
POST /api/points-mall/order/create HTTP/1.1
Content-Type: application/json

{"goodsId":"005","num":1,"points":1,"userId":"<本人>"}
```

对照基线（正常兑换 100 积分档商品）：

```http
{"goodsId":"001","num":1,"points":100,"userId":"<本人>"}
```

判据：响应返回订单号且订单详情显示商品为 005（1000 积分档），而账户实际扣减为 1 积分（或 100 积分）——即「商品档位与扣减额不一致」。

## 变体与关联

- 字段变体：`goodsId`/`productId`/`skuId`/`itemId`、`points`/`integral`/`score`/`credit`、`amount`/`payAmount`；也常见于「兑换码 + 商品 ID」组合参数。
- 时序变体：在「进入结算页」时校验商品与积分，而在「提交订单」时只按请求里的编号重新落库，形成校验与落库的商品不一致（本卡主场景）；反向的时序问题见负数量抵消类卡。
- 同类参数信任：优惠券 ID、地址 ID、发票 ID、赠品 ID、档位 ID 只要按客户端值查询而不校验归属/适用性，都可用同一思路测试。
- 关联：[[web-generic-payment-amount-tamper-no-order-binding]]（改支付金额而非商品编号）、[[web-generic-payment-negative-quantity-offset]]（改数量为负数抵消金额）、[[web-generic-auth-coupon-id-parameter-tampering-idor]]（改券 ID 而非商品 ID）。

## 检测与防御

- **服务端定价**：商品编号只能来自「服务端维护的购物车/兑换单」，下单时校验编号属于该单据；所需积分/金额一律按服务端商品表重算，禁止接受客户端提交的抵扣值或应付值。
- **一致性校验**：订单快照在「确认兑换」时固化商品与数量，支付/发货环节只读快照，不接受再次提交的编号；校验与落库使用同一份数据。
- **范围与次数**：对积分扣减做非负与上限校验，兑换接口做限购与幂等（同一单据只允许一次成功提交）。
- **检测特征**：同一用户在短时间内以不同 `goodsId` 提交结构相同的兑换请求；请求中的 `points`/`amount` 与商品表应有值不符；订单商品档位与扣减积分不匹配；兑换成功后立即取消/退款。
