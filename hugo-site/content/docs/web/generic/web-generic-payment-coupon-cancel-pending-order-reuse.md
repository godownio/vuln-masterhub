## 一句话结论

同一账号可在两台设备同时登录时，先在手机 A 用优惠券创建订单并停留在支付页不付款，再在手机 B 取消该订单让优惠券立即返还，然后用返还的券在手机 B 重新下单，最后两台手机同时支付；由于取消订单没有使 A 的待支付订单/支付会话失效，同一张券最终抵扣了两笔订单。

## 原理

- 优惠券在下单时通常被“锁定/占用”，在订单取消或超时未支付时释放回用户账户。正常流程要求“取消订单”与“该订单的支付能力”同时失效，保证同一张券最多服务一笔成功交易。
- 该应用的缺陷在于状态机没有把两者绑定：
  1. 手机 A 下单后，订单处于“待支付”，优惠券状态为“已使用/锁定”，A 停留在支付页面（支付页面已持有订单号/支付参数）。
  2. 手机 B 对同一账号取消该订单，服务端把优惠券释放回账户，但没有让 A 页面上的支付会话/订单失效（或 A 页面可直接用缓存的支付参数继续支付）。
  3. 手机 B 用已返还的同一张券创建第二笔订单并进入支付页。
  4. 两台手机同时支付：A 的旧订单和 B 的新订单都带着同一张券的折扣，支付通道各自成功，形成“一券两单”。
- 根因是优惠券的“使用”与“支付成功”不是同一个原子状态：取消只回滚了订单状态与券状态，没有校验/撤销已生成的支付单，也没有在支付回调时再次校验券是否仍绑定该订单、是否已被其他订单使用。

## 触发条件

- 应用支持同一账号在多台设备同时登录（原文用两个手机）。
- 优惠券在下单时锁定、取消订单时立即返还，且返还后旧订单的支付页面仍可支付（支付参数未失效）。
- 两笔订单都使用同一张券，服务端在支付回调时不再校验券的唯一使用状态。
- 攻击者拥有两个可同时登录的设备/会话，并能完成真实支付（或至少让两笔支付都成功）。

## 利用步骤

1. 手机 A 登录账号，进入会员/商品购买页，选择可用优惠券创建订单，停在支付页面不付款。
2. 手机 B 登录同一账号，找到该待支付订单并点击“取消订单”。
3. 观察优惠券已返还到账户（券列表重新出现同一张券）。
4. 手机 B 立即用返还的券创建第二笔订单，进入支付页面。
5. 两台手机同时点击支付，两笔订单分别使用同一张券的折扣并支付成功。
6. 在订单列表确认两笔订单都已支付且都享受了优惠，造成平台资金损失（原文会员年费场景每单减 118 元）。

## PoC

无脚本 PoC；原文为手工双设备操作，关键步骤截图包括：手机 A 的支付页 ¥180、优惠券列表、取消订单按钮、券返还后的券列表、手机 B 再次下单。

时间线示意：

```
A: create order(coupon=X) -> payment page (hold)
B: cancel order -> coupon X returned
B: create order(coupon=X) -> payment page
A + B: pay simultaneously -> both orders discounted by X
```

## 变体与关联

- 同类状态机缺陷：取消/退款后积分、礼品卡、满减券未与旧支付单解绑；旧支付链接/二维码仍可支付。
- 与 `web-generic-race-condition-coupon-concurrent-claim-stack` 的区别：该卡是领取接口并发重复领取；本卡是取消订单返还券后与滞留支付页组合复用。
- 与订单并发复用券卡的区别：本卡不一定需要高并发，利用的是“取消返还 + 旧支付页仍有效”的状态错位；两者可组合。
- 其他支付逻辑卡：`web-generic-payment-amount-tamper-no-order-binding`、`web-generic-payment-negative-quantity-offset`。

## 检测与防御

- 优惠券与订单强绑定：下单锁定券时生成唯一占用记录，取消/超时只释放该记录；支付回调必须校验券仍绑定本订单且未被其他订单使用。
- 取消订单时同步关闭支付单/支付会话，使旧支付页面、二维码、支付参数立即失效；支付网关侧做订单状态校验。
- 优惠券使用记录加唯一约束（券 ID + 用户）与幂等键；同一券只允许一笔“支付成功”的订单。
- 监控：同一用户短时间内取消订单后又用同一券下单、同一券出现在多笔已支付订单、同一账号多设备并发支付。
- 业务侧：对“取消后立即复用同券”做风控规则；支付成功回调二次校验订单与券状态。
