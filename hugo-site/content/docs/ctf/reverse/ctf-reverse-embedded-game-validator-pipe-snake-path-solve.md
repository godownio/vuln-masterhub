## 一句话结论

当主程序把真正的校验器藏成一个内嵌 PE、又在运行时用命名管道与它通信时，flag 不再由「算法比对」决定，而是由「游戏必须通关」决定：先在 IDA 里按 MZ 头把内嵌 PE dump 成独立文件、逆出两端的管道协议，再从校验器里读出「每步与字节表比较 → 命中就下发食物坐标」的规则，然后用分数规则反推投食时机，写一个离线的贪吃蛇模拟器搜出满足全部条件的那条路径，路径编码（hex）就是 flag。

## 原理

- **校验器被藏进内嵌 PE**：主程序 `main` 只做壳，真正的判断在 `sub_4013C0` 起始的一段数据，从该地址往下看是标准 `MZ` 头。用 IDA 脚本按字节区间 `fputc(Byte(i), fp)` 导出成 `dump` 文件直接再拖进 IDA，就能看到干净的校验逻辑——比在壳里对着花指令硬读省事得多。
- **flag 的格式先由外层定**：外层 check 只做三件事——长度必须是 36、前 5 字节必须是 `flag{`、末字节必须是 `}`，然后把 `{}` 中间的 30 个 hex 字符两两解成 15 字节（`<=57` 走 `-48`，否则 `-87`）。也就是说真正的「内容」是 15 字节、每字节对应游戏的一步。
- **15 字节 = 15 步的决策表**：内嵌 PE 里对每个 `i` 判断 `v4[i] == byte_414D18[v11]`，命中则把「第几位」和「食物坐标 `v11%5, v11/5`」通过管道下发；`v11 == 25` 表示这一步不下发食物（题目规定有三步不投食）。于是 flag 的每一字节都唯一编码了一条验证信息：走第几个方向 + 在哪一格投食。
- **分数曲线让「何时投食」可算**：贪吃蛇的分数从 5 开始，每移动一步减 1，吃到食物加 `dword_40D61C`（初值 3，每吃一次 +2）。因此分数序列被完全确定：`5-4-3-2-1-(4)-3-2-1-(6)-5-4-3-2-1-(8)`，括号处就是必须投食的步。序列证明了「投食时机」不是自由的，而是被分数规则逼出来的固定节拍。
- **通关条件与失败条件都写在模拟器里**：`dword_40D618 == 8` 时返回「成功」；分数 `<=0`、`>8`、蛇头越界（`>4`）、撞到自身、食物没吃对位置，都会返回失败码（`3306`/`25565`/`53`）。所以求解 = 在「必须投食的步」上让食物正好落在蛇头前方，其余步保持安全移动。
- **管道两端用标准算法通信**：`sub_3D1940`/`sub_3D1900` 是没改动过的 SM4（加/解密），负责传输数据的保密；它不影响 flag 的求解，但解释了两端为什么能安全交换「食物坐标」这类状态。理解这点可以避免把时间浪费在 SM4 上（它没有魔改，也没有参与 flag 校验）。
- **为什么必须「离线重建」而不是硬算**：走位受食物位置、蛇身增长、分数节拍三重约束，逐字节爆破不成立；只有把游戏规则完整复刻成模拟器，才能对候选路径快速判定，进而搜索出唯一解。

## 触发条件

- 主程序体量异常小、`main` 里只是启动一个子模块（IPC/管道/进程注入），真正的逻辑不在主模块。
- 内存或数据段里能搜到第二个 `MZ`/`PE` 头，或其地址区间紧邻 `.data` 尾部（常见「资源内嵌可执行文件」手法）。
- 校验与「游戏状态」相关：程序里有分数、坐标、边界判断、失败码这类游戏要素。
- flag 的可见格式（长度/前后缀）由外层先校验，中间段是定长编码。
- 能拿到两端通信的协议（结构体布局 / 报文格式），或至少能动态观察到每次交互的内容。

## 利用步骤

1. 静态定位内嵌模块：在主模块里搜 `MZ` 头，或从 `main` 调用的「可疑大函数」跟进去看数据首字节；确认起止地址。
2. dump 出来：用 IDA 脚本按字节区间导出（`for i in range(start, end+1): fputc(Byte(i), fp)`），把产物当新 PE 单独分析。
3. 逆外层格式：找出长度/前缀/后缀校验与 hex 解码循环，确认「中间 30 字符 → 15 字节」。
4. 逆内层校验：找到 `v4[i] == byte_table[v11]` 这类逐字节比较，弄清 `v11` 的含义（本例是「食物在一维表里的下标」），以及 `v11 == 25` 的特例语义。
5. 逆游戏规则：分数初值/衰减/吃食物加成、蛇身增长、边界、失败返回码、成功条件；把分数序列手算出来，标出必须投食的步。
6. 写离线模拟器：输入 15 字节候选路径，按规则推演，输出是否达成「分数 == 8 且不触发任何失败码」；再用 DFS/剪枝（每步只有少数合法方向）搜索。
7. 把解出的 15 字节 hex 拼回 `flag{...}`，用原程序跑一遍验证。

## PoC

dump 内嵌 PE（IDA IDC）：

```c
#include <idc.idc>
static main() {
    auto i, fp;
    fp = fopen("dump", "wb");
    for (i = 0x426980; i <= 0x43D57F; i++)
        fputc(Byte(i), fp);
}
```

外层格式与 hex 解码（等价伪码）：

```c
if (strlen(input) != 36) fail();
if (strncmp(input, "flag{", 5)) fail();
if (input[35] != '}') fail();
for (i = 0; i < 15; i++) {
    a = hexval(input[5 + 2*i]);      // '0'-'9' -> -48, 'a'-'f' -> -87
    b = hexval(input[6 + 2*i]);
    step[i] = (a << 4) | b;          // 15 字节决策表
}
```

内层「命中即投食」的判定（决定求解约束）：

```c
for (i = 0; i < 15; i++) {
    if (step[i] == byte_table[v11]) {
        if (v11 == 25)  send(i, NO_FOOD);          // 规定不投食的步
        else            send(i, v11 % 5, v11 / 5); // 食物坐标
    }
}
```

求解器骨架：

```python
def play(steps):
    score, grow, snake, head, food = 5, 3, [(0,0)], (0,0), None
    for i, s in enumerate(steps):
        head = move(head, s)                 # 方向与字节表一致
        if out_of_board(head) or head in snake: return False
        if food and head == food:
            grow += 2; score += grow; snake.append(snake[-1])
            food = None
        else:
            score -= 1
        if score <= 0 or score > 8: return False
        if must_feed(i): food = expected_food(i)   # 由分数曲线反推
    return score == 8
```

上面 `move`/`byte_table`/分数曲线的具体数值来自二进制与内嵌 PE 的常量表，换题必须重新提取；本卡的 `play` 只是约束骨架，不是可直接运行的完整解。

## 变体与关联

- 校验载体变体：内嵌 PE 可换成内嵌 shellcode、DLL、dotnet 程序集、Lua/WASM 脚本；dump 手段随之变化（内存 dump、`LoadLibrary` 断点、资源节提取）。
- 游戏类型变体：贪吃蛇之外还有推箱子、扫雷、迷宫、俄罗斯方块——共同点是「flag 编码了通关操作序列」，都需要复刻规则后搜索。
- 通信变体：命名管道可换成 socket、共享内存、文件、注册表；关键不是通道本身，而是「通道里传的内容即校验数据」。
- 加密变体：本例管道用标准 SM4（未魔改），若换成魔改版就要先逆算法再解协议；判断方法是找 SM4 的 FK/CK/S 盒常量与 32 轮结构。
- 关联：与「内嵌 PE 释放/自解密」类卡的区别是本条不涉及加壳，内嵌 PE 是明文可见的校验模块；与「游戏布尔状态定位」类卡的区别是那张讲用 CE 找内存状态，本卡讲离线复刻规则求解。

## 检测与防御

- 属 CTF 逆向范畴；工程上把「校验逻辑」与「游戏/交互逻辑」耦合到需要通关才能验证，只是提高分析成本，不构成安全边界。
- 若用于授权校验，应把判定放在服务端并对结果签名，不要依赖客户端可复刻的模拟器规则。
- 分析侧自检：遇到「主程序极小 + 内嵌 MZ + 分数/坐标」三件套，优先 dump 内嵌模块并找常量表，比在壳里逐条读花指令快得多；先确认传输加密是否魔改，未魔改就跳过它。
