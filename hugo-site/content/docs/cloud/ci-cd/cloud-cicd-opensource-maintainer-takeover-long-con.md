## 一句话结论

攻击者用约两年时间扮演一个此前没有在线足迹的热心贡献者，配合多个马甲账号在邮件列表向身心俱疲的单人维护者施压、推动其移交维护/发布权限，最终把后门伪装成测试数据和构建脚本修复带进上游发布并被下游发行版打包——开源供应链最有效的入口往往不是代码漏洞，而是对人的长期经营。

## 原理

- **目标选择**：优先挑依赖面大但维护资源薄弱的“无聊”基础库。xz-utils 长期由 Lasse Collin 单人维护，维护者公开提到自己有健康问题、进度落后；这类项目 bus factor 为 1，维护者本身渴望有人接手，且下游（发行版、systemd 通知补丁等）使实际依赖面远超项目表面。
- **建立可信身份**：2021 年 10 月出现的 “Jia Tan”（GitHub `JiaT75`）此前没有任何在线足迹，之后持续提交高质量补丁、参与维护，逐步从外部贡献者变成共同维护者与发布经理。
- **马甲施压**：不久后出现几个明显同伙的傀儡账号，在邮件列表公开质疑维护者进度、要求交出控制权，制造“项目需要新人接手”的舆论压力；维护者据称在 2023 年某个时候让出了权限。
- **长期经营**：潜伏约两年，先做真实维护工作（包括向仓库添加二进制测试文件、参与发布流程），把恶意改动混进正常发布节奏。这批问题提交的时间分布与平时不同（出现在不寻常的时间段），可用于推测攻击者时区与作息。
- **发布与下游推动**：后门的一部分只存在于发布 tarball 的构建脚本中，git 仓库保持干净；随后攻击者与新的马甲账号开始联系 Linux 发行版维护者，以“重要新功能 / 修复 valgrind 报错 / 文档与翻译修正”等理由催促打包 5.6.x。Fedora 打包者事后回忆：对方连续几周推动把 xz 5.6.x 加入 Fedora 40/41，还一起排查过后来被证明由后门引起的 valgrind 问题；Ubuntu 上的同步请求甚至在披露前一天仍在提交。
- **为什么难以发现**：审查默认“长期贡献者 = 可信”，review 聚焦 C 代码，构建脚本和二进制测试文件属于低关注面；release tarball 与 git 仓库很少逐字节比对；下游打包者与上游维护者是熟人关系，社交催促容易绕过技术怀疑。
- **暴露**：由外部工程师在排查 SSH 登录变慢与 valgrind 报错时发现，并非靠权限系统或代码审查拦住。

## 触发条件

- 目标上游项目依赖广泛，但维护者只有一人或极小团队，且维护者疲惫、公开寻求接手者；
- 项目治理允许新贡献者逐步获得 commit / release 权限，缺少双人复核与发布权限隔离；
- 发布流程存在低审查面：构建脚本、打包生成的 `.m4`/`configure`/`Makefile.in`、二进制测试数据、tarball 与 git 不一致的文件；
- 下游发行版有“上游新版本即打包”的惯性，打包者与上游维护者存在直接沟通渠道；
- 攻击者具备多年耐心、多个身份与持续产出真实补丁的能力。

## 利用步骤

1. 选定 bus factor 低、下游影响大的基础库，研究维护者健康/精力状况、社区关系与现有治理。
2. 创建一个无历史足迹的身份，持续数月到数年提交真实、有价值的补丁与维护工作，积累信任与话语权。
3. 用若干马甲账号在 issue / 邮件列表制造“维护者应放权、项目需要新的维护者”的舆论压力。
4. 获得 commit / release 权限后保持正常维护节奏，把恶意内容伪装成测试文件、构建修复、文档修正等低审查面改动。
5. 在发布窗口把后门带入 release 产物（例如只存在于 tarball 的构建宏/脚本），保持 git 仓库干净以防代码审查发现。
6. 主动联系下游发行版打包者，以“bug 修复 / 重要新功能”推动升级；必要时配合排查自身引起的异常，维持可信形象。
7. 等下游大规模集成后启用后门；通过控制提交时间、身份行为与沟通方式降低归因线索。

## PoC

无 PoC（这是社会工程与长期运营过程，不是代码漏洞）。可核对的最小证据链：同一身份在约两年内从外部贡献者变为发布经理；多个无历史账号集中向原维护者施压；恶意改动只出现在 release tarball 的构建脚本与二进制测试文件中；披露前一天仍在催促发行版同步新版本。

## 变体与关联

- 与“直接窃取维护者账号或发布 token”的短平快投毒不同，本手法是合法获取权限，2FA、签名等账号安全措施无法防御，只能靠治理与产物比对。
- 对应的技术后门链见 [[code-analysis-cve-xz-liblzma-supply-chain-backdoor-ifunc-got-sshd]]；npm/PyPI 等包仓库投毒多走 postinstall、依赖混淆或包名抢注，属于不同入口。
- 变体：伪造履历的“影子贡献者”、以赞助/雇佣名义进入维护团队、接管废弃包名或无人维护的项目。

## 检测与防御

- **治理**：关键依赖避免 bus factor = 1；commit 权限与 release 权限分离；双人发布与强制 review；维护者交接公开审计与冷静期。
- **产物一致性**：对 release tarball 与 git tag 逐文件/逐字节比对，重点关注构建脚本、打包生成物、二进制测试数据与未被测试引用的文件；使用可复现构建与产物哈希。
- **行为信号**：账号年龄与历史足迹异常、贡献时间分布突变、多个新账号集中施压维护者、发布前夕频繁催促下游升级、对构建/测试数据的“修复”过度热情。
- **下游防线**：打包者不应仅凭上游私交或 “bugfix only” 描述直接接受新版本；对基础设施类库升级做差异审计与来源验证。
- **应急**：确认上游被接管后冻结相关版本、回滚/升级、轮换密钥并审计构建产物与下游分发范围。
