## 一句话结论

调试器在目标地址首字节写入 `0xCC`（x86 的单字节 `INT 3`），程序执行到该处触发断点异常并交给调试器；命中后调试器恢复原字节、让原指令单步执行一次，再把 `0xCC` 写回。因此“断点”本质是对代码的就地字节补丁，API 断点（BP/BPX）、条件断点、条件记录断点、消息断点底层都是同一种 CC 断点，只是命中判断和后续动作不同。

## 原理

- **INT3 是单字节指令**：`0xCC` 只占一个字节，替换任意指令首字节都不破坏后续指令的地址与对齐，因此调试器可以就地实现断点。
- **异常接管**：CPU 执行 `0xCC` 产生断点异常（`STATUS_BREAKPOINT`），处于被调试状态的进程由内核把异常交给调试器，调试器暂停程序并展示寄存器、栈、内存现场。
- **恢复-单步-回写流程**：继续运行前，调试器把原字节写回；为了执行这条原指令又不丢失断点，通常借助单步标志（EFLAGS.TF）或临时断点，让 CPU 执行完这一条后再次触发单步异常，调试器重新写入 `0xCC`。所以调试期间进程内存中的代码与磁盘文件不一致。
- **两个视图不一致**：OllyDbg 的反汇编/内存视图显示原始字节，是为了方便分析（调试器自己知道那里有断点）；用 Cheat Engine 等第二个工具直接读取目标进程内存，会看到首字节已经变成 `CC`。这是验证“断点是否真的落地”的直观方法。
- **特殊断点同源**：`BP MessageBoxA` 是在 API 函数入口首字节下 CC；`BPX MessageBoxA` 是在模块间调用列表中对该 API 的所有调用指令下 CC；条件断点在 CC 命中后先计算逻辑表达式，不满足就自动继续；条件记录断点在此之上记录表达式/参数值；消息断点是在窗口过程入口按 `[ESP+8]` 的消息号过滤。它们都不是另一种“魔法”，只是 CC 断点加上过滤器和附带动作。
- **为什么能被发现**：代码段出现预期之外的 `0xCC`，或代码段 CRC/校验和与磁盘映像不符，就是软件断点存在的证据；反过来，硬件断点、内存断点不写代码字节，可用于对抗这类自校验。

## 触发条件

- 目标为可被调试的用户态程序（x86/x64 PE）。
- 目标代码页可写，或调试器能够临时修改页保护；只读代码页需要先 `VirtualProtect` 才能写入 `0xCC`。
- 目标未对代码段做 CRC/首字节扫描等自校验，或分析者已绕过校验。
- 分析者需要观察某条指令执行时的寄存器/内存状态，并且可以接受调试期间代码字节被改写。

## 利用步骤

1. 在反汇编窗口定位要观察的指令（选中其首字节）。
2. OllyDbg 中用 `F2`、双击该行，或右键“断点 → 切换”设置断点；在 BreakPoint 窗口统一查看、启用、删除断点。
3. 运行程序直至命中，检查寄存器、栈、内存与调用堆栈，完成分析。
4. 怀疑断点未生效或被目标自校验破坏时，用 Cheat Engine 等第二工具读取该地址首字节：若为 `CC` 说明断点确实写入；OllyDbg 自身视图仍显示原指令属正常现象。
5. 目标存在代码字节校验时，撤销 CC 断点，改用硬件断点或内存断点继续分析（见关联卡）。

## PoC

无 PoC（调试器操作技巧）。

## 变体与关联

- **硬件断点**：用调试寄存器 Dr0–Dr3 监视地址，不写代码字节，能通过 CRC/首字节扫描。
- **内存断点**：改页保护属性而非字节，同样不改代码。
- **VEH 隐形断点**：用 `int 0x2C`、除零、非法访问等异常替代 `0xCC`，在进程内异常处理中接管，避免留下 CC 特征。
- **反调试的 0xCC/CRC 校验**：属于对软件断点的检测与反制，绕过思路包括改用硬件断点或修补校验比较结果。
- 条件断点、条件记录断点、消息断点均为 CC 断点加过滤条件，分别见对应卡片。

## 检测与防御

- **检测**：程序可扫描自身代码段是否出现 `0xCC`、对代码段计算 CRC/校验和并与磁盘映像比对，或检测代码页写属性变化，从而发现软件断点或调试器。
- **防御/对抗**：加壳、代码段只读化、启动早于调试器自校验、多处交叉校验都会提高 CC 断点的使用成本；分析者一侧则改用不修改代码字节的硬件断点/内存断点，或在校验点下断修改结果。
- 调试器在自身视图中隐藏 CC 只影响其自己的显示，不影响其他进程/工具读取真实内存，因此“OllyDbg 看不到 CC”不能作为断点不存在的依据。
